# Goal Form Setup Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace quotas, priorities and text setup with one form per goal (name, category, hours per week); the
engine schedules each goal from its own hours; the weekly review becomes a read-only summary.

**Architecture:** Deletions first (text setup and AI extraction, then priority proposals), each leaving a
compiling, green build. Then one backend task changes the `Goal` model end to end (domain → engine → persistence
→ Flyway V4 → API → agent tools), because removing `priority` breaks every layer at once. Then the frontend, then
docs.

**Tech Stack:** Spring Boot 4.1 / Java 21, JPA + Flyway on Postgres 17 (pgvector), Testcontainers; React 19 + TS,
Vitest + Testing Library.

**Spec:** `docs/superpowers/specs/2026-10-28-goal-form-setup-design.md`

## Global Constraints

- Goal ids stay `<categoryId>-<slug(name)>`; no kept goal gets a new id. Fixed blocks unchanged by the migration.
- Already-stored days are never regenerated by this change.
- `minutesPerWeek`: integer, 0..10080, multiple of 30. New goal defaults: `defaultBlockMinutes` 60,
  `Energy.MEDIUM`, `PreferredTime.ANY` (today's `Goal.withDefaults`).
- Schema changes only via `backend/src/main/resources/db/migration/V4__goal_hours.sql` (Hibernate `validate`).
- Old chat proposals with `kind: PRIORITIES` must still deserialize and render, read-only.
- Spec 5.5 lists `PriorityChange` and `PriorityProposalCard` as removed but also requires old proposals to render;
  ruling: both stay as **read-only** (no producer, no apply, no buttons). Everything that creates or applies them
  goes.
- Frontend: shared controls, `.card`, `btn-*` per `frontend/UI.md`; no raw `<select>` / date / time inputs.
- Working agreement: before each commit, stage, show `git diff --cached --stat`, wait for the user's approval.
  Backend tests need Docker (`docker compose up -d`).

## Review Focus

1. Saved setup with goals referenced by past blocks: after V4 and a Save, goal ids are identical → Task 3
   migration test asserts goal ids and fixed-block rows survive V4 unchanged.
2. Old thread containing an APPLIED priority proposal loads through `GET /api/assistant/chat` and renders without
   buttons → Task 2 `ChatService` test + Task 4 `ChatPanel` test.
3. Hours entered as "1,5" (comma decimal) or "1.3" → Task 4 `editSetup` tests: comma accepted as 1.5, 1.3 flagged.
4. Weekly summary that mentions "Gym has been postponed twice" must not be bounced by `ReplyGuard` → Task 2 test.
5. Goal with 0 h right after migration shows the hint and gets no blocks, no warning → Task 3 engine test, Task 4
   editor test.
